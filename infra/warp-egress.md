# WARP egress for the sim host (botflow-mba-26)

All egress from the prod sim box exits via Cloudflare WARP instead of the home
ISP IP: user apps running in simulators, build-VM traffic (SPM/git fetches from
untrusted project builds), ASC uploads — everything. Ingress was already on a
Cloudflare Tunnel (`sim.botflow-site.app`); with WARP the home network is no
longer an exit node for any user-controlled traffic.

## Components

| Piece | Where | Why |
|---|---|---|
| Cloudflare WARP client (consumer) | `/Applications/Cloudflare WARP.app`, daemon LaunchDaemon | The tunnel itself. **Mode: `tunnel_only`, protocol WireGuard.** Full "warp" mode fights mDNSResponder for port 53 (which serves DNS to the build-VM NAT subnet) and wedges in `Unable`; MASQUE never completed its handshake on this network. |
| `com.botflow.warp-watchdog` | LaunchDaemon, 120s + RunAtLoad | Consumer WARP has no reliable connect-on-boot; this reconnects it. Script: `infra/warp-watchdog.sh`. |
| `com.botflow.vmnat` PF anchor | generated by `pf-egress-load.sh` | Build-VM egress. vmnet's own NAT breaks under WARP (WARP's PF firewall RSTs non-tunnel flows on sight — visible as instant forged RSTs on bridge100). The anchor `route-to`s guest traffic into the WARP utun and source-NATs it to WARP's own tunnel address (`172.16.0.2`), which WARP's `pass out quick on <utun> from <addr>` rule then accepts. Fail-closed: WARP down ⇒ guests get no egress, never a raw-IP leak. |
| sshd `Match Address 192.168.64.0/24 → DenyUsers *` | `/etc/ssh/sshd_config.d/100-botflow-deny-vm-subnet.conf` | vmnet delivers guest→host traffic in userspace, bypassing PF entirely, so untrusted build scripts could otherwise reach the host's sshd. PF can't see that traffic; sshd itself must refuse it. |

## Verified (2026-07-29)

- Host trace `warp=on`, Cloudflare egress IP; WARP stats 0.00% loss, 13ms.
- Guest trace from a build VM: Cloudflare IP, `warp=on`; real SPM clone from
  github inside a device build: 20–22s builds.
- Mario sim sessions 3/3 streaming 36–43s via the public endpoint.
- Guests blocked from: router panel, LAN, tailnet, host gateway (except DNS/DHCP);
  sshd closes the vmnet-bypass hole (verified `Connection closed` pre-auth).
- cloudflared ingress rides WARP fine (it reconnects itself after WARP state
  changes; brief 502s during transitions only).
- Cold-reboot recovery: WARP watchdog reconnects, guard reloads anchors
  (see `postboot-verify` results in the session logs).

## Operational notes

- **Tailscale management path now relays via DERP** (direct UDP path doesn't
  survive the WARP + inter-VLAN setup). SSH sessions can reset during Tailscale
  path churn — run long remote work `nohup`'d with a log file, always.
- The WARP utun name can change on reconnect; the pf guard (300s) rewrites the
  vmnat anchor when it moves. Worst-case gap ≈ 5 min of no guest egress.
- `/tmp` is cleared on macOS reboot — persistent tooling lives in
  `/Users/botflow/e2e/`, not `/tmp`.
- Registration is a consumer WARP registration made on-box (TOS accepted
  2026-07-29 with owner approval). `warp-cli registration show` for details.
- NEXT (deferred): ER605 VLAN-20 egress allowlist so nothing can bypass WARP
  even if misconfigured — allow only WARP endpoints (162.159.192.0/24 &c.,
  UDP 500/1701/2408/4500 + TCP 443), Tailscale coordination/DERP, DNS.
